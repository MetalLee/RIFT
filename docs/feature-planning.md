# 按功能拆分与验收

聊天 Lead 和独立 Workflow Lead 在运行时共用 `src/task/planning-policy.ts`，已有工作区也会收到该规则，不覆盖用户保存的角色配置。规则用于开发任务，不要求普通讨论创建计划。

不增加强制规划轮次、分析任务或重复审核，沿用现有检查与审查流程。

默认一个任务完成一个可独立验收的功能，包括所需界面、接口、数据／协议变更和必要测试。小改动或紧密耦合的改动保持在一起，不为占满开发槽位拆任务。专业分工或跨仓交付需要拆分时，写明接口契约和最终联调负责人；一个正式任务仍只绑定一个仓库。

任务 `instructions` 应说明用户结果、范围与不包含内容、需保留的行为、依赖契约及验证方法。任务级 `acceptanceCriteria` 写可观察的行为、相关错误或边界场景和所需证据。分析任务则说明问题与预期产物。此规则属于模型规划指引，API 保持兼容，不以关键词检查强制判断任务质量。

计划级 `acceptanceCriteria` 保持原有继承语义，会加入每一个任务，仅适合真正通用的要求。不要把整个工作流的最终结果放在这里。跨功能验证只在存在交互时安排，并依赖相关功能。收尾前 Lead 对照原始目标检查遗漏；Host 的 finish 门禁只能确认已登记任务通过，不能自动证明需求覆盖完整。

例如：公共协议确需调整时先完成该前置任务，然后并行开发“通知设置”和“任务搜索”，每个任务自行完成全栈和相关验证；只有存在交互时再增加跨功能验证。公共注册点、迁移和共享协议的语义依赖由 Lead 通过 `dependsOn` 表达。`expectedPaths` 不是权限边界或调度锁，独立 worktree 不消除合并冲突。

Lead 根据配置成员与预算派发独立任务；连续功能工作或专业能力需要时指定 `roleName`，其他任务可由调度器选择空闲成员。依赖成功后后继才执行，代码依赖还需已接受提交。返工沿用现有成员／会话选择机制。

任务输入 `dependencyContext` 包含直接依赖的任务与仓库 ID、状态、已接受提交、当前 attempt 的成功开发／分析 Run ID、结果产物 ID 和每条最多约 2000 字节、合计约 8000 字节的脱敏摘要（标记是否截断）。不传递原始日志、提示词或失败 attempt 的结果。无持久化产物时产物 ID 为 null；完整记录通过 task show/evidence 查询。摘要是开发者陈述，不是当前任务的测试或验收证明。内容作为任务输入快照保存，后续执行重新读取依赖状态。
